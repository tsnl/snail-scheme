## Native optimization caveat

This freeze supplied already optimized V8 program Wasm to a native helper that
always runs Binaryen. Native therefore optimized the program a second time.
These correctness outcomes do not establish execution from identical optimized
Wasm on both targets. This is the same pipeline distinction documented in the
[six-case optimization audit](20261015-native-optimization-audit.json).

| Case | V8 program Wasm | Native second-pass Wasm | LLVM text | Native outcome |
| --- | ---: | ---: | ---: | --- |
| Primes | 3,334 B | 612,417 B | 41,857,797 B | Build and canonical execution passed |
| GCBench | 22,424 B | 879,977 B | 111,616,338 B | Build timed out after 1,800.121 s |

Both expansions occurred in the second Binaryen pass, before LLVM lowering.
The optimized Wasm, textual Wasm and LLVM artifacts are retained at their exact
paths and hashes in the report. GCBench's supervisor recorded return code -9,
`timeout: true`, and no executing descendants after cleanup. Its Wasm, both
Chez controls and both Rust routes passed; no native execution is claimed.

Future one-pass native validation belongs to a separate freeze and must check
actual optimized program byte equality. It cannot replace this failed attempt
or convert these diagnostic durations into performance samples.
